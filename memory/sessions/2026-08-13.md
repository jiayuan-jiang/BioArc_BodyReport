User reported two issues in one message: (1) species search via iNaturalist is fine, but a "no match" result
shouldn't block submission, and (2) elevation fetches from open-elevation.com have become unstable for an
unclear reason, with an API key applied for but not yet received by email.

For (1): traced `Step1Specimen.jsx`'s validation. A clean autocomplete response with zero results left
`form.speciesSci` empty forever, since `clearSelection()` wipes it on every keystroke and only a dropdown
click or a genuine *fetch failure* ever repopulated it — the success-with-zero-results path never did. Fixed
by falling back to the typed text on a zero-result success response too, matching the existing fetch-failure
fallback. Verified in-browser: typed a nonsense species name, confirmed "No species found" showed, selected a
preservation method, clicked Next, form advanced normally (previously would have shown a required-field error
and refused to advance).

For (2): investigated directly rather than trusting the "maybe it's the pending key" theory. Repeated live
tests against `api.open-elevation.com/api/v1/lookup` (both GET and the documented POST form) all hung with
zero response for the full 10s timeout — a real backend outage/overload on their end, unrelated to the API
key (a missing/invalid key would 401/403, not hang the TCP connection). Open-Meteo already runs a free, no-key
elevation endpoint (Copernicus GLO-90) on the same host this app already calls for weather, and answered
correctly in ~0.6s on every test. Switched `fetchElevation()` in `environmentApi.js` to try Open-Meteo first,
falling back to Open-Elevation only if that fails too (kept as a fallback rather than dropped, in case it
recovers or the pending key changes its reliability later).

Found one more real bug while verifying (2) in-browser: the Elevation card's sub-label was the static string
"SRTM via Open-Elevation", accurate when there was only one source but now wrong most of the time since
Open-Meteo answers first. Updated to "Copernicus DEM via Open-Meteo" (all 4 languages) and reordered/reworded
the Sources footer citations to match, without building full per-record source-provenance tracking (unlike the
land-cover mislabeling fix from 2026-08-12) since this was a static label, not a per-submission field.

Verified everything end-to-end via Chrome browser automation against the local dev server: no-match species
submission, real species search still matching correctly, elevation resolving via Open-Meteo with the
corrected label, and `npm test` (7 tests, unrelated to either change) still passing throughout.
