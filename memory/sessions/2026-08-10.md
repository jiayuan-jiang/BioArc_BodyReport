# Session 2026-08-10

User asked, conversationally first, how a full offline mode should be designed given the app's actual field
constraints: species search can't hit the live iNaturalist API with no signal, and environmental data can't
be fetched at Step 3 time either, needing to be deferred until resubmission and keyed to the original
collection timestamp rather than "now." Answered that as a scoped recommendation (automatic
`navigator.onLine` detection, no manual toggle; species search was already degrade-safe; env fetch needed
to move from immediate to deferred+backfill; a real local queue needs IndexedDB not localStorage because of
the `File`/`Blob` photos; and a service worker is a separate, only-if-needed layer for the app shell itself
to load offline) before writing any code, per the "exploratory question" convention — then the user confirmed
they wanted the full thing built, including the PWA layer, since field use with no connectivity is a real
scenario for this app.

Implemented the full design from `spec/offline.md` (written this session, see it for the complete writeup):

- Added `vite-plugin-pwa` (new dev dependency, noted in `state.md` per the "no new dependencies without
  noting" rule) in `generateSW` mode. Generated `public/icon.svg` from the existing header logo (green
  background, white stroke), rasterized via `rsvg-convert` (available on this machine, no new dependency)
  into `pwa-192.png`/`pwa-512.png`/`maskable-512.png`/`apple-touch-icon.png`/`favicon-32.png`. Runtime
  caching added for OSM tiles, the Leaflet CDN marker assets, and Google Fonts; deliberately did NOT cache
  any of the live data APIs or `/api/kobo-submit` — those go through the app-level offline logic below, not
  a stale cache standing in for live data.
- `environmentApi.js` gained `fetchEnvironmentData()` (extracted from `Step3Environment.jsx`'s inline
  `Promise.allSettled` fan-out, now shared) and `resolveEnvironment(form)`, which backfills using the form's
  original `collectionDate`/lat/lng rather than whenever the sync happens to run, and never overwrites a
  manually-entered field.
- `Step3Environment.jsx`: skips the fetch when offline (or when it comes back completely empty even while
  nominally online), sets `form.envFetchPending`, shows a deferred/retry banner, but leaves manual field
  entry available and never blocks `Next`.
- New `src/offline/` module: `db.js` (IndexedDB wrapper — `localStorage` can't hold the `File`/`Blob` photo
  objects), `queue.js` (`enqueueSubmission`/`processQueue`, stops the batch on a `TypeError` — real
  connectivity failure — but keeps going past a single record's non-network rejection), `OfflineContext.jsx`
  (`navigator.onLine` + `online`/`offline` listeners, auto-syncs on reconnect plus a 5-minute fallback poll).
- `Step5Review.jsx` now queues locally instead of failing when offline, or when a submit attempt throws a
  `TypeError` specifically (fetch's own signal for a genuine network failure) — a real Kobo 4xx/5xx
  rejection (a plain `Error` from `koboApi.js`) still surfaces to the user immediately instead of being
  silently queued and retried forever. `koboApi.js`'s `submitToKobo()` now takes an optional `instanceId` so
  a retried record keeps a stable ID.
- New `OfflineBadge.jsx` header component: connectivity pill + pending count, opens a panel listing queued
  records with relative time, error text if a retry failed, manual "Sync Now," and a per-record discard
  (`window.confirm`-gated). `App.jsx` wraps everything in `OfflineProvider` and gives the success screen a
  distinct "Saved on This Device" state when `onSuccess` was called with `queued: true`.
- Added every new user-facing string to all 4 languages in `i18n/index.jsx` (removed the now-unused
  `s3_error`/`s3_error_cont` keys, replaced by the deferred/retry copy) and matching CSS in `index.css`.

Verified with a clean `vite build` after each major edit, then a full click-through in a real browser against
`vite preview` (simulating offline by overriding `navigator.onLine` + dispatching `online`/`offline` events,
since that's the exact signal the app itself watches): filled Steps 1-2 normally (species search live, map
pin via typed coordinates), forced offline before Step 3 mounted — confirmed the amber deferred banner +
Retry button appeared, all env fields showed `—`, and `Next` stayed enabled. Step 5 showed the offline notice
and a "Save Offline" button; submitting produced the "Saved on This Device" success screen with a stable ID
and put the header badge at "Offline · 1". Opened the queue panel and confirmed the record listing (species,
date, relative time). Flipped back online (`online` event) and watched `processQueue()` fire automatically:
badge went to "Syncing…" then landed on an `error` state with `KoboToolbox error 404` — expected, since
`vite preview` doesn't run the Vercel `/api/kobo-submit` function (a pre-existing, already-documented local-
dev limitation, not a regression).

**Found and fixed a real bug during this test.** Inspecting the IndexedDB entry after that failed sync
showed `envFetchPending` was still `true` and elevation/temperature/landCover were still `null`, even though
`resolveEnvironment()` should have backfilled them using the real (working) environment APIs before the
submit attempt failed. Root cause: `processQueue()` in `queue.js` reassigned a local `form` variable when the
backfill succeeded, but the `catch` block persisted `{...entry, status: 'error', ...}` — the *original*
`entry`, whose `.form` was never updated — so a successful env backfill was silently discarded every time the
subsequent submit failed. Fixed by writing the reassigned `form` back into the persisted entry on error too.
Rebuilt, hard-reloaded (unregistered the SW + cleared caches to pick up the new bundle), and re-ran the sync:
confirmed `elevation: 27`, `temperature: 20.2`, `landCover: "Cemetery"` (real data for the test coordinates,
Boston) now persist correctly and `envFetchPending` flips to `false`, surviving repeated retries without
re-fetching. This is exactly the kind of bug that would have silently cost researchers their environmental
data on every offline record that also happened to hit a submission error, so worth having caught before
merging. Cleaned up the test queue entry directly via IndexedDB (the panel's own discard button uses
`window.confirm`, which blocks the page and is not compatible with the browser-automation tooling used for
this test session, though it's normal and fine for a real human user clicking it).
