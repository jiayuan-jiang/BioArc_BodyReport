User reported broken photo thumbnails via a screenshot from the deployed app (a "cat.jpg" upload showing the
browser's broken-image icon). Reproduced live with Chrome browser automation against the local dev server:
uploaded a real JPEG through the Step 1 dropzone and confirmed the resulting `blob:` thumbnail had
`naturalWidth`/`naturalHeight` of 0 and fetched to a 4-byte blob. Isolated the root cause outside React
entirely: `Step1Specimen.jsx`'s `handleFiles` called `valid.map(compressImage)`, and `Array.prototype.map`
passes `(element, index, array)` to its callback, so `compressImage(file, maxDim = 1280, quality = 0.75)`
received `index` as `maxDim` and the whole `array` as `quality`. The first photo in every batch got
`maxDim = 0`, producing a 0×0 canvas whose `toBlob` silently resolves to a near-empty stub instead of
throwing, which is why there was never a console error to chase. Fixed with `valid.map(f => compressImage(f))`
and re-verified in-browser: same file now compresses correctly (800×600, 3609 bytes) and renders in the
thumbnail grid. Documented in `context/state.md` under Known Issues (marked fixed).

Follow-up on the photo-upload fix above: user asked whether HEIC (the format iOS photo-library uploads
actually arrive in) was handled at all. It wasn't, despite the UI advertising "JPG, PNG, HEIC". Confirmed two
separate bugs live in-browser with a real `.heic` test file: Chrome reports HEIC's `file.type` as
`application/octet-stream` rather than `image/heic`, so the existing `f.type.startsWith('image/')` filter
silently dropped it before processing; and even past that filter, Chromium has no built-in HEIC decoder at
all, `createImageBitmap()` throws `InvalidStateError` directly (Safari is the only engine with native HEIC
support). Fixed by widening the filter to also match the `.heic`/`.heif` extension, and adding `heic-to`
(WASM libheif, ^1.5.2) as a `createImageBitmap` fallback, dynamic-imported only when a HEIC file is actually
encountered so the ~3MB decoder never bloats the main bundle. Also swapped `Promise.all` for
`Promise.allSettled` in `handleFiles` so one undecodable file no longer kills every other photo in the same
batch, with a new `s1_err_photo_decode` i18n string (all 4 languages) surfaced when a file is skipped.
Verified in-browser: real HEIC file now converts to a correct 800×600 JPEG, and a deliberately corrupt file
mixed into a batch gets skipped while the valid JPG next to it still succeeds. Documented in `context/state.md`
under Known Issues and the Tech Stack table.
