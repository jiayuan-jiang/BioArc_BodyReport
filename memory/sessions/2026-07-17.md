# Session 2026-07-17

User reported the Submit button on Step 5 did nothing. Investigation found the root cause was worse than a
frontend bug: `koboApi.js` POSTed JSON to `/api/v2/assets/{uid}/submissions/`, an endpoint that returns 404 —
KoboToolbox's REST API v2 has no action to create a submission at all (confirmed via `OPTIONS` on `/data/`:
only list/retrieve/delete/duplicate/validation/enketo actions exist). New submissions only go in through the
OpenRosa XML protocol.

Fixed in three parts:
1. Added the missing environment fields to the live Kobo form (`dem_elevation_m`, `land_cover_lucc`,
   `weather_temperature`, `weather_precipitation`, `weather_wind_speed`, `weather_code`) via `PATCH
   /api/v2/assets/{uid}/` on `content.survey`, then redeployed with `PATCH /api/v2/assets/{uid}/deployment/`
   passing the new `version_id` explicitly — a plain `{"active": true}` PATCH is a no-op redeploy and silently
   keeps serving the old version, which cost some time to figure out.
2. Rewrote `koboApi.js` to build a proper OpenRosa XML instance: single `location` geopoint field (was 4
   separate lat/lng/alt/acc fields that don't exist on the form), `notes` (was `additional_notes`),
   `preservation_method` value mapping (`frozen→freeze`, `dried→dry` — the frontend's values don't match the
   Kobo choice list), and the photo attached as a real multipart file part. The XML root must be
   `<data id="{ASSET_UID}">` — the `id` has to be the asset UID, not the form's xlsform `id_string`
   ("specimen_survey"); Kobo remaps the form's OpenRosa `formID` to the asset UID internally, confirmed via
   `formList`.
3. Discovered mid-testing (via a real Playwright click-through, not just curl) that Kobo's OpenRosa
   `/submission` endpoint sends **no CORS headers at all** — a direct browser `fetch` from any origin is
   permanently blocked. Added `api/kobo-submit.js`, a Vercel serverless function that proxies the raw
   multipart body server-side (no parsing, just forwards + injects `Authorization`), and moved
   `KOBO_API_KEY`/`KOBO_BASE_URL`/`KOBO_OWNER_USERNAME` to non-`VITE_`-prefixed server-only env vars (the API
   key was previously bundled into client JS, visible in DevTools — fixed as a side effect of this rework).

Verified end-to-end twice: first an isolated Node script running the exact `koboApi.js` code confirmed the
XML/multipart logic against the real Kobo backend; then a full Playwright browser click-through of all 5 form
steps against `vite dev` + a local mock of the Vercel function (proxied via a temporary `vite.config.js`
change, reverted after) produced the real "Submission Complete" screen. Both test records were inspected via
the Kobo data API (fields + photo attachment landed correctly) and deleted afterward.

Found but explicitly out of scope (already tracked, not silently fixed): `Step1Specimen.jsx`'s species picker
is a hardcoded North American wildlife list with slug-style values (e.g. `procyon_lotor`) that has no relation
to the Kobo form's actual `species` choices (scientific names like `Panthera onca`, `Lama glama`). Confirmed via
test submission that the raw slug lands in Kobo unmatched against any choice. This was already the top
"in progress" task-queue item (migrate to iNaturalist API); bumped its priority note since it now also explains
why species data won't map to Kobo's dropdown correctly, not just staleness.
