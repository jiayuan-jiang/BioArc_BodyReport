Conversation started as a discussion, not a coding task: the user asked (in Chinese) whether the environmental
metadata BioARC already auto-fetches (elevation, land cover, weather, soil) actually matters to researchers
archiving specimens. Answered with domain reasoning rather than code changes: static site descriptors
(elevation, land cover) are standard Darwin Core / MIxS covariates and genuinely useful for niche modeling;
point-in-time weather/soil readings are narrower in value (mostly phenology/behavior studies), and are
technically re-derivable later from the stored lat/lon + date anyway — the real added value of the app's
design is the manual-override + provenance tracking (`env_manual_fields`/`env_fetched_snapshot`), which
lets a field researcher's instrument reading beat a remote estimate without losing the original fetched value.

distance to protected-area boundary is more niche/specialized, not a general SDM covariate.

User came back with the real root cause: the icon disappears specifically after navigating back to Step 2
and forward to Step 3 again — not a caching issue at all. Found it: `status` is local `useState('idle')`
state in `Step3Environment`, which unmounts on navigating away (App.jsx only renders the step matching
`step === 3`) and remounts fresh on return. The actual env data lives in the parent `form` state and
survives fine across remounts, but `status` doesn't — it resets to `'idle'`, and the mount `useEffect` only
handled "never fetched" and "fetch pending," never "already fetched successfully in an earlier mount." Since
the refetch button, success banner, and edit hint are all gated on `status !== 'idle'` / `status === 'done'`,
they all silently vanished on any revisit even though the underlying data was fine. Fixed by setting
`status` to `'done'` immediately when `form.elevation !== null` on mount. Verified in-browser: fetched once,
clicked Back then Next, confirmed the icon and banner both persisted immediately with the same data.

Lesson for this codebase: any UI element gated on Step3Environment's local `status` state needs to account
for the component remounting on every step navigation — mirrors the earlier "verify API limitations before
writing them off" lesson in spirit: don't assume a symptom's most likely cause (deployment/cache) without
checking against what the user actually described (a specific navigation sequence, not "it's just broken").

User reported it *still* wasn't working after that push ("我这还是没有啊"). Before re-explaining anything,

[[feedback_diagnose_from_repro_steps]] taken one step further: even after verifying the *previous* fix
worked, a "still broken" report needs fresh verification of deployment + service health before looking for a
new bug — and the new bug here was a latent design flaw (unbounded penalty for a transient failure) that
existing tests hadn't caught because they didn't span a long-enough session to hit a transient blip.

The actual mitigation for this class of failure is the graceful degradation already built in (null field,
manual edit-pencil, no submission block), not further endpoint chasing.
